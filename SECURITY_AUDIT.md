# Auditoría de seguridad — TVA

Fecha: 10/09/2026. Se revisaron rutas, componentes, formularios, hooks, servicios Supabase, Worker, SQL, políticas, scripts, dependencias, configuración y entorno local. Se inspeccionó el esquema del proyecto Supabase autorizado. El repositorio contenía cambios de implementación previos sin commit: se conservaron. Esta revisión no es una certificación ni un pentest de infraestructura del proveedor.

## Estado inicial

La aplicación ya tenía RLS en once tablas, claves publicables, roles separados, RPC transaccional con precios autoritativos, bloqueo de stock e idempotencia. No se comprobó una vulnerabilidad de manipulación de precios ni lectura pública de pedidos. Había exposición innecesaria del servidor de desarrollo, dependencias con avisos, ausencia de cuotas propias en checkout, ausencia de auditoría y cabeceras, y comprobaciones administrativas que no consultaban revocación de sesión en cada operación de datos.

## Cambios realizados

Código: Worker y nuevo módulo de cabeceras; Vite loopback; errores tipados; comprobación de usuario/sesión; fuentes y archivos de imagen; selección de campos del panel; comparación de stock al editar; invalidación de recursos ante error. Nuevas pruebas SQL/de seguridad y escáner ligero. Sin nueva arquitectura de autenticación ni eliminación de comercio.

Supabase: aplicada `supabase/migrations/202609100002_security.sql` después de la migración comercial. Se comprobó éxito de la transacción y posteriormente **12 tablas con RLS, 10 triggers de auditoría, EXECUTE anónimo falso en la función interna, 8 productos conservados, 0 pedidos y bucket limitado a 5.242.880 bytes**. El registro público cerrado y Confirm email activo provenían de la configuración anterior; no son cambios atribuidos a esta migración. No se alteraron cuentas, contraseñas, precios, stock ni pedidos reales durante las pruebas.

RLS: matriz completa por tabla en SECURITY.md. Se añadió lectura administrativa de audit; `is_admin` reforzado afecta todas las políticas administrativas existentes. Storage: reemplazadas las políticas de INSERT/UPDATE por políticas con ruta/producto, preservadas SELECT público y DELETE solo administrador. Se reafirmaron límites MIME/tamaño. No se cambiaron buckets públicos a privados ni se movieron archivos.

Dependencias: Next 16.3.4, React/React DOM/RSC 19.3.0, Vite 8.0.16, Vinext 1.0.0-beta.9, plugin RSC 0.5.34, Cloudflare Vite 1.54.6, Wrangler 4.130.0, workers-types 5.20260910.1, eslint-config-next 16.3.4; transitivas compatibles mediante audit fix sin force. Override sharp 0.35.4, probado decodificando una imagen local. Se retiró drizzle-kit y su comando de generación, que solo correspondían al D1 desactivado y arrastraban esbuild antiguo. Se conservan configuración ilustrativa, ORM y ejemplos. Vinext sigue siendo prerelease: mantener pruebas de regresión al actualizar.

## Evidencia de verificación

Pruebas nuevas y existentes se ejecutan sobre PostgreSQL PGlite desechable con esquemas mínimos de Auth/Storage. No son un ataque contra Supabase ni un sustituto de concurrencia multiconexión. Los fixtures no llegan a producción.

Comandos: `npm test`, `npm run test:components`, `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:rendered`, `npm run security:check`, `npm audit`, `npm run db:check`. Resultados finales: 26 comprobaciones de lógica/SQL/seguridad, 4 de componentes y 11 del Worker aprobadas; lint y TypeScript sin errores ni advertencias; build correcto; db:check real aprobado; npm audit con cero vulnerabilidades; escáner sin hallazgos. No se usó `npm audit fix --force`. El entorno restringido de Windows bloqueó inicialmente tsx; se ejecutó con permisos locales adecuados y las pruebas terminaron.

## Pendientes, riesgo residual y checklist de publicación

- [ ] Gateway antiabuso con CAPTCHA verificado servidor y rate limit por IP; revocar el RPC público después de verificar el gateway. Mientras siga público, se puede agotar cuota/stock con identidades falsas.
- [ ] Vencimiento transaccional de reservas y procedimiento de pedidos pendientes.
- [ ] MFA con enrolamiento/challenge en panel y cuenta operadora; recuperación probada.
- [ ] Inspección/recodificación de uploads en servidor si se amplían los permisos o se exige una garantía de contenido.
- [ ] Validar CHECK de datos antiguos, revisar Security Advisor y evitar exponer esquema private.
- [ ] SMTP, URLs exactas de autenticación y CAPTCHA si se habilitan altas de alumnos.
- [ ] Verificación TLS/CSP/HSTS sobre dominio publicado y assets CDN. El sitio no se ha desplegado en esta fase.
- [ ] Backups y restauración, responsables, retención de PII/logs y revisión periódica de dependencias.
- [ ] Pruebas en staging de concurrencia entre conexiones y uploads completos por rol; no se cargaron binarios de prueba ni pedidos ficticios al proyecto real.
- [ ] CI con permisos mínimos cuando exista remote/plataforma elegida. Propuesta incluida en SECURITY.md.

No hay evidencia actual que exija rotar service_role/secret. Una filtración descubierta posteriormente sí exige rotación e investigación, aunque el archivo ya se haya borrado.

**Valoración: ACEPTABLE para desarrollo controlado; todavía no listo para operación comercial pública.** La autorización es efectiva fuera del frontend, se cerraron fallos comprobados y el runtime se actualizó. No corresponde calificarlo BUENO/MUY BUENO para producción mientras el checkout anónimo pueda ser abusado y falten los controles operativos descritos. El hardening realizado es verificable; esos pendientes quedan abiertos, no maquillados como correcciones completas.
